# RFC-037.1 — Vigilancia Semanal de Maestros (VSM)

**Estado:** Adendum operativo de RFC-037
**Cadencia:** Semanal, lunes 06:00 UTC
**Ámbito:** Todas las ramas DAM con maestros absorbidos o en estudio
**Principio asociado:** Principio 6 — Vigilancia y depuración continua

## 1. Propósito

Los maestros externos evolucionan. Aparecen nuevas versiones, correcciones, regresiones, deprecaciones y motores nuevos. ARKI debe vigilar esos cambios sin adoptar nada automáticamente.

La VSM garantiza que el conocimiento absorbido siga siendo correcto, trazable y útil. También permite purgar reglas que se demuestren incorrectas.

## 2. Ciclo semanal

```text
DETECTAR → EVALUAR → ABSORBER | DESCARTAR → PURGAR → REGISTRAR
```

El ciclo produce un reporte semanal, pero no modifica automáticamente el runtime ni las reglas graduadas.

## 3. Paso 1 — Detectar

Leer el registro de maestros desde:

```text
data/master_registry/masters.json
```

Para cada maestro:

- Consultar la versión disponible en sus fuentes declaradas.
- Compararla con `version_actual`.
- Detectar cambios de versión, releases, deprecaciones y cambios de licencia.
- Registrar fallos de consulta como `INSUFFICIENT_DATA`.
- Buscar motores nuevos en categorías relevantes.
- Proponer motores nuevos sin absorberlos automáticamente.

### Salida

```text
data/master_registry/logs/YYYY-MM-DD_weekly_review.md
```

El reporte debe clasificar maestros como:

- Con nueva versión.
- Sin cambios.
- Nuevos detectados.
- Obsoletos: sin actualización en dos años o más.
- No consultables.

## 4. Paso 2 — Evaluar

Cada cambio se evalúa contra las reglas y ground truths de la rama correspondiente. La evaluación debe usar evidencia reproducible: changelog, documentación oficial, benchmark, fixture, test o comparación visual.

### Clasificaciones

| Código | Clasificación | Acción |
|---|---|---|
| A | Mejora relevante | Adoptar después de reproducir ground truth y extraer reglas |
| B | Mejora neutra | Registrar; no adoptar por defecto |
| C | Regresión | No adoptar; congelar versión anterior y documentar |
| D | Mejora sin evidencia | No adoptar hasta obtener evidencia |
| E | Deprecación | Migrar a la alternativa oficial y registrar deuda técnica |
| F | Cambio de licencia | Detener adopción y consultar al Product Owner |

Una nueva versión nunca se adopta solo porque sea más reciente.

## 5. Paso 3 — Absorber o descartar

### Mejora relevante

1. Instalar la versión nueva únicamente en el entorno de aprendizaje.
2. Ejecutar el mismo ground truth que se usó con la versión anterior.
3. Comparar calidad, comportamiento, rendimiento y estabilidad.
4. Adoptar solo si el resultado mejora o al menos no empeora.
5. Reextraer las reglas afectadas.
6. Actualizar el conocimiento con la fuente y la evidencia.

### Mejora neutra

Registrar la versión y el análisis. No modificar las reglas propias si el cambio no afecta el conocimiento absorbido.

### Regresión

Mantener la versión anterior congelada. No copiar el comportamiento regresivo. Registrar el caso para futuras revisiones.

### Mejora sin evidencia

No adoptar. La afirmación del proveedor no sustituye un benchmark o ground truth reproducible.

### Deprecación

Migrar a la alternativa oficial solo después de comprobar que conserva el comportamiento absorbido. Registrar la deuda técnica y la prueba de migración.

### Cambio de licencia

Detener la adopción y solicitar revisión del Product Owner antes de utilizar la versión nueva.

## 6. Paso 4 — Purgar

La purga se aplica cuando una regla absorbida se demuestra incorrecta mediante evidencia reproducible.

### Procedimiento

1. Localizar la regla en:
   - `data/drawing_knowledge/arki_learned_rules.json`.
   - `src/sicl/<rama>/arki_*.py`.
   - Tests y fixtures relacionados.
   - Otros datos o módulos derivados.
2. Verificar la incorrección mediante test, comparación con un maestro actualizado o documentación oficial.
3. Eliminar la regla del código, JSON y tests relacionados.
4. No comentarla, no dejar un TODO y no conservar código muerto.
5. Ejecutar nuevamente la suite de la rama.
6. Registrar la purga en el historial.
7. Hacer commit con el formato:

```text
purge(vsm): remove incorrect rule <nombre_regla> from <rama>
```

### Regla dura

Una regla demostrada incorrecta se borra. No se conserva “por si acaso”.

Si una purga afecta más de tres reglas relacionadas, el procedimiento se detiene y requiere consulta al Product Owner.

## 7. Paso 5 — Registrar

Cada revisión debe dejar un registro con:

| Campo | Contenido |
|---|---|
| Fecha | Fecha UTC de revisión |
| Maestro | ID del registro |
| Versión anterior | Versión usada por ARKI |
| Versión nueva | Versión detectada |
| Fuente | URL, paquete, repositorio o release |
| Clasificación | A, B, C, D, E o F |
| Evidencia | Test, benchmark, fixture o changelog |
| Acción | Adoptar, registrar, descartar, purgar o detener |
| Revisor | Agente o persona responsable |
| Commit | Commit relacionado, si existe |

## 10. Registro de maestros

El inventario debe mantener esta estructura:

```json
{
  "masters": [
    {
      "id": "ifcopenshell",
      "name": "IfcOpenShell",
      "ramas": ["dibujo", "bim"],
      "fuentes_version": [
        {"type": "pip", "package": "ifcopenshell"},
        {"type": "github", "repo": "IfcOpenShell/IfcOpenShell"}
      ],
      "version_actual": "0.8.5",
      "fecha_ultima_revision": "2026-09-26",
      "estado": "absorbido"
    }
  ]
}
```

## 11. Automatización

El script semanal debe ejecutarse los lunes a las 06:00 UTC y publicar el reporte como artifact. Si detecta cambios críticos, puede abrir un issue con la etiqueta `vsm-review-required`.

La automatización solo detecta y reporta. No actualiza paquetes, no modifica reglas, no purga código y no absorbe cambios.

## 12. Relación con DAM

VSM implementa el Principio 6 de RFC-037. La vigilancia protege los otros cinco principios:

- Evita que un maestro se convierta en dependencia ciega.
- Permite conservar aportes válidos de motores imperfectos.
- Exige fuente para cada regla.
- Mantiene la síntesis como propiedad de ARKI.
- Impide que una nueva versión externa entre directamente al runtime.
